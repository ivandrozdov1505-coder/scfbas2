# Технический аудит ProfitBox_v2.4 (single-file HTML)

## 0) Контекст и рамки
- Проанализирован реальный код `ProfitBox_v2.4.html`.
- Переписывание кода не выполнялось: отчёт фиксирует карту зависимостей, риски и пошаговый план безопасной миграции в React.
- Приоритеты: не ломать расчёты, не терять функции, не деградировать mobile-first UX.

## 1) Краткая карта проекта

### 1.1 Сущности данных
- **products** — карточки товаров: цены, qty, stock, minStock, заметки, изображение, папка.
- **folders** — пользовательские категории с цветом.
- **saleDocs / supplyDocs** — источники истины для продаж/поставок в документном виде.
- **sales / purchases** — «плоские» проекции документов (rebuildFlatOpsFromDocs).
- **expenseOps** — отдельные расходы (общие и привязанные к товару).
- **customNotes** — ручные заметки.
- **UI/state-параметры**: текущая вкладка, фильтры, сортировки, тема, режим скидки, диапазон аналитики, авто-бэкап.

### 1.2 Основные вкладки и сценарии
- **Каталог**: CRUD товара, сортировка/поиск, быстрая продажа, дублирование.
- **История**: продажи / поставки / расходы + фильтры.
- **Склад**: остатки, порог, статус, корректировка stock.
- **Аналитика**: метрики по диапазону дат, графики, дельты к прошлому периоду.
- **Заметки**: агрегация заметок из операций + ручные заметки.
- **Сервисные сценарии**: экспорт JSON/CSV/XLS, import JSON, backup/restore, темы, мобильная навигация.

### 1.3 Ключевая бизнес-логика
- Миграция/нормализация данных `migrateData` + восстановление плоских операций `rebuildFlatOpsFromDocs`.
- Расчёты прибыли на момент продажи (`profitAtSale`, `costAtSale`) через `computeSaleSnapshot` / `getActualProfitForSale`.
- Поддержка консистентности `qty/stock` при продаже, поставке, ручной корректировке.
- Агрегация аналитики по периодам и сравнением к предыдущему диапазону.

### 1.4 Наиболее связанные части
- `saleDocs/supplyDocs` ↔ `sales/purchases` ↔ `stock/qty` (самый высокий риск).
- Каталог (`products.expenses`) ↔ История расходов (`expenseOps`) ↔ аналитика/маржа.
- UI-рендер + `persist` + `liveUpdate` + автосохранение/автобэкап.
- Мобильные layout-режимы (портрет/landscape-phone) тесно завязаны на CSS-классы и JS-переключение.

## 2) Список проблем по категориям

## 2.1 Баги

1) **Счётчик истории в liveUpdate не учитывает расходы**  
- Факт: `renderSidebar` считает `sales+purchases+expenseOps`, а `liveUpdate` — только `sales+purchases`.  
- Риск: пользователь видит прыгающее/неконсистентное число после операций.  
- Критичность: **Medium** (доверие к интерфейсу).  
- Исправление: единый селектор `getHistoryCount()` и использование в обоих местах.

2) **Удаление расхода меняет `product.expenses`, хотя добавление расхода его не меняет**  
- Факт: `addExpenseOp` пишет только в `expenseOps`, но `delExpenseOp` уменьшает `p.expenses`.  
- Риск: «дрейф» карточки товара, потенциально отрицательный тренд расходов в каталоге при серии операций.  
- Критичность: **High** (искажение финансовых данных).  
- Исправление: разделить «базовые расходы карточки» и «операционные расходы истории»; не мутировать `product.expenses` в `delExpenseOp`.

3) **Восстановление удалённого товара может ломать id-счётчики документов**  
- Факт: в undo для товара поднимаются `nextSaleLineId/nextSupplyLineId`, но не `nextSaleDocId/nextSupplyDocId`; документы добавляются обратно «как есть».  
- Риск: коллизии id при последующих вставках документов в крайних сценариях.  
- Критичность: **Medium**.  
- Исправление: после undo пересчитывать max id для doc/line или перейти на UUID.

4) **Дублирование календарного блока-комментария**  
- Факт: двойной заголовок секции CUSTOM CALENDAR.  
- Риск: шум и путаница при сопровождении.  
- Критичность: **Low**.  
- Исправление: убрать дубликат комментариев.

## 2.2 Логические ошибки/неоднозначности расчётов

1) **`recalcStockFromHistory` игнорирует purchases**  
- Факт: функция строит purchasedMap, но не использует его; stock = qty - sold.  
- Риск: зависимость от того, что `qty` уже «впитал» поставки; при импорте/частичных миграциях логика может быть хрупкой.  
- Критичность: **High** при миграции данных.  
- Исправление: явная формула `stock = purchased - sold (+opening)` или жёстко документировать текущую модель `qty = cumulative purchased`.

2) **`profitDelta` считается только если `prevProfit > 0`**  
- Факт: при нуле/отрицательном прошлом периоде дельта скрывается (`null`).  
- Риск: пользователь не видит изменения в сложных периодах (из минуса в плюс).  
- Критичность: **Medium**.  
- Исправление: ввести безопасную метрику (например, абсолютная разница + отдельный бейдж «из убытка в прибыль»).

3) **Две разные модели расходов в одном интерфейсе**  
- Факт: `products.expenses` участвует в `calcFor`, а `expenseOps` — в аналитике периода/истории.  
- Риск: расхождение «Прибыль каталога» vs «Факт/Net за период», сложность объяснения пользователю.  
- Критичность: **High** (доверие к отчётам).  
- Исправление: закрепить доменную модель (Opening/Base expenses vs Period expenses) и отобразить это явно в UI.

4) **Редактирование `qty` в карточке принудительно пересчитывает `stock = qty - sold`**  
- Факт: ручное изменение `qty` может неожиданно «переписать» остаток.  
- Риск: пользователь теряет ожидаемое значение склада.  
- Критичность: **Medium**.  
- Исправление: разделить поля «первичный приход/всего куплено» и «текущий остаток», либо добавить явный confirm.

## 2.3 Производительность

1) **Глобальный `setInterval(liveUpdate, 2000)` + тяжёлые проходы**  
- Факт: каждые 2 сек пересчёты/DOM-обходы даже без изменений.  
- Риск: лишняя нагрузка на мобильных, батарея, лаги на больших наборах данных.  
- Критичность: **High** для mobile.  
- Исправление: event-driven обновления; interval только как fallback с адаптивным backoff.

2) **Много O(n²) участков при рендере/экспорте/операциях**  
- Факт: частые `filter/reduce` внутри циклов по товарам/операциям.  
- Риск: деградация на 1k+ записей.  
- Критичность: **Medium**.  
- Исправление: мемоизированные словари (`soldByProduct`, `purchaseByProduct`, `folderByIdMap`) на один проход.

3) **Полный `render()` при большинстве действий**  
- Факт: практически любой input/change триггерит полную перестройку вкладки.  
- Риск: заметная задержка на слабых смартфонах.  
- Критичность: **Medium**.  
- Исправление: компонентный рендер (React) + локальные обновления состояния.

4) **Хранение base64-изображений в localStorage**  
- Факт: картинка в `products.image`; localStorage ограничен (~5MB).  
- Риск: тихие ошибки сохранения при росте каталога с фото.  
- Критичность: **High** для реального использования.  
- Исправление: IndexedDB/OPFS для бинарных данных, в state хранить только ссылки/идентификаторы.

## 2.4 Поддержка кода

1) **Монолит ~3000 строк в одном файле (UI+стили+бизнес+storage)**  
- Риск: высокая стоимость изменений, высокий регрессионный риск.  
- Критичность: **High**.
- Исправление: декомпозиция по модулям/слоям (domain, storage, ui).

2) **Переопределение функций через обёртки (`switchTab`, `persist`)**  
- Риск: неявный порядок вызовов, сложно отлаживать side-effects.  
- Критичность: **Medium**.  
- Исправление: централизованные middleware/hooks событий вместо monkey patch.

3) **Inline-обработчики `onclick` + строковый HTML**  
- Риск: XSS-поверхность и трудность рефакторинга/типизации.  
- Критичность: **Medium**.  
- Исправление: декларативные компоненты + явные handlers.

4) **Дублирование ответственности (например, статы в `renderSidebar` и `liveUpdate`)**  
- Риск: расхождение поведения (уже проявилось в счётчике истории).  
- Критичность: **Medium**.  
- Исправление: один источник вычислений селекторов состояния.

## 2.5 Адаптивность / mobile-first

1) **Очень плотный и хрупкий CSS с множеством `!important` и жёстких grid-шаблонов**  
- Риск: локальная правка ломает другой breakpoint.  
- Критичность: **High**.
- Исправление: токены + контейнерные компоненты + визуальные регресс-тесты по брейкпоинтам.

2) **Отдельный landscape-phone режим на классах `body.layout-landscape-phone`**  
- Риск: сложно перенести без 1:1 поведенческой совместимости (sidebar, topbar, nav).  
- Критичность: **High**.
- Исправление: вынести layout-shell как отдельный компонент и сохранить переключение режима.

3) **Hover-зависимости в мобильном контексте (меню topbar-more, folder-actions)**  
- Риск: UX на тач-экранах непредсказуем.  
- Критичность: **Medium**.  
- Исправление: явные tap-триггеры/aria-expanded состояния.

## 2.6 UX-проблемы

1) **Несогласованность финансовых терминов/метрик между вкладками**  
- Риск: пользователь неверно интерпретирует прибыль.  
- Критичность: **High**.  
- Исправление: унификация словаря метрик + tooltip «как считается» для каждой карточки.

2) **Undo-окно короткое (5 секунд) и без истории**  
- Риск: случайные удаления не успевают откатить.  
- Критичность: **Medium**.  
- Исправление: увеличить TTL, добавить центр «Недавние действия».

3) **Сильная зависимость от alert/confirm**  
- Риск: прерывает поток действий, особенно на mobile.  
- Критичность: **Low/Medium**.  
- Исправление: неблокирующие toast/modal-подтверждения.

## 3) План миграции в React по этапам (без поломки логики)

## Этап 0 — Заморозка логики и «контракт данных»
- Выделить и зафиксировать доменную модель: `Product, Folder, SaleDoc, SupplyDoc, ExpenseOp, CustomNote`.
- Формализовать инварианты:
  - `sales/purchases` = projection от docs;
  - `stock >= 0`, `qty >= stock`;
  - `profitAtSale` immutable snapshot.
- Вынести pure-функции расчётов и миграций в отдельный модуль (без UI).
- Добавить snapshot-тесты на существующем наборе JSON-файлов.

**Проверки после этапа:**
- Golden-тесты для `migrateData`, `rebuildFlatOpsFromDocs`, `getActualProfitForSale`, аналитики диапазонов.

## Этап 1 — Data Layer без React UI
- Внедрить `store` (например, Zustand/Redux Toolkit) поверх текущего HTML (strangler pattern).
- Перенести storage-адаптеры (localStorage, backup/import/export) в отдельные сервисы.
- Убрать переопределения `persist/switchTab`; заменить на action middleware.

**Проверки:**
- Повторяемость действий: add/edit/delete sale/purchase/expense + undo.
- Идемпотентность persist/load/import/restore.

## Этап 2 — Shell и мобильная навигация в React (первыми)
- Перенести **только каркас**: sidebar/topbar/mobile-nav/overlay/layout-mode.
- Сохранить CSS классы/структуру 1:1 на первом шаге.
- Существующие вкладки временно монтировать как legacy island/bridge.

**Проверки:**
- Визуальный parity: 360×800, 390×844, 768×1024, landscape ≤900.
- Навигация и открытие/закрытие mobile sidebar.

## Этап 3 — Каталог + История (критическое ядро)
- Перенос `products` и операций продаж/поставок/расходов на React-компоненты.
- Сначала — формы и CRUD без изменения формул.
- Только после parity — оптимизация и рефакторинг.

**Проверки:**
- Contract-тесты расчётов по фиксированным сценариям.
- E2E: создание товара → поставка → продажа → удаление/undo → восстановление из backup.

## Этап 4 — Склад и аналитика
- Перенос тяжёлых таблиц, графиков и фильтров.
- Удаление polling `setInterval(liveUpdate)` в пользу реактивных селекторов.

**Проверки:**
- Производительность: time-to-interact, render time на 100/1000 товаров.
- Сопоставление KPI старой и новой версии по одинаковому JSON.

## Этап 5 — Заметки, экспорт, документация, hardening
- Перенос notes/export/import/backup UI.
- Внедрение feature flags + progressive rollout.
- Для изображений перейти с localStorage на IndexedDB (миграция по месту).

**Проверки:**
- Обратная совместимость импорта старых дампов.
- Корректный экспорт CSV/XLS/JSON.

## 4) Что переносить первым, что временно оставить

### Переносить первым
1. Data contracts + pure расчёты + миграции.
2. Shell/layout/mobile-nav.
3. Каталог + История (продажи/поставки/расходы).

### Временно оставить как есть
